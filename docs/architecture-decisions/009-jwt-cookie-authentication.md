# ADR 009 · JWT cookie access with database-checked rotating sessions

Status: implemented for the explicitly authorized Phase 4. This supersedes ADR 003's opaque **access** format only; the historical decision is retained. Refresh and action tokens remain opaque random secrets stored as hashes. No tenant authorization or workspace membership is implemented.

The latest Phase 4 brief explicitly requests JWT access tokens. Use maintained jose, HS256 with an environment-supplied random key of at least 32 bytes, strict algorithm/type/issuer/audience/subject/session/version/expiry checks, and a 10-minute default lifetime. Store access credentials only in HttpOnly cookies; never return them in JSON or localStorage. The JWT contains identifiers and authentication epoch, without email, roles or tenant grants.

Every protected request also checks MongoDB's current account and session. Logout, logout-all, reset and disable therefore invalidate access immediately on subsequent checks. This deliberately keeps a database lookup rather than promising purely stateless JWT authorization. Database failure fails closed.

One session document is one device/family. Refresh is `sessionId.randomSecret`, SHA-256 hashed in storage. Transactions serialize the user authentication guard with an atomic session hash comparison/replacement and consumed-hash history. Recognized replay commits revocation before returning 401. Concurrent raw rotations fail closed; the browser uses single-flight and Web Locks, rechecking the cookie session after taking the lock. History is capped at 512; overflow requires login. Expiration is checked in queries, independent of TTL cleanup.

Keep production host-only `__Host-fw_*` cookies Secure/HttpOnly/SameSite=Lax/Path=/ without Domain. HTTP development uses separate `fw_*` names. Production assumes same-origin or same-site HTTPS; unrelated registrable domains are not supported by this cookie policy. Exact credentialed CORS and signed session/pre-session-bound double-submit CSRF replace the planned database synchronizer implementation while preserving its trust boundary. HMAC domain separation, HttpOnly context cookies, constant-time comparisons, a one-hour nonce limit, exact Origin checks and Fetch Metadata rejection protect every unsafe auth request, including login. SameSite alone is insufficient.

Registration remains generic 202 for both new/existing addresses, rather than returning a creation-only user DTO that explicitly reveals account existence. Safe user data is returned after verified login/me. The latest routes `/auth/register` and `/auth/me` replace the historical planned `/auth/signup` and `/users/me` names. No compatibility alias or business endpoint is falsely advertised as operational.

Mail dispatch follows the committed token write, is tracked for bounded shutdown and excludes provider latency from the generic public response. Local capture is development/test only and never exposed by HTTP. Production requires configured TLS SMTP. Delivery failure is logged with a static code; responses do not claim acceptance. There is no durable mail outbox: crash recovery uses the real resend/recovery workflow.

The unique email index is authoritative under races. Login/reset/logout-all/refresh write a user guard in transactions to serialize security transitions. Index creation is additive and fails on conflicts; no collection, index or existing Atlas data is dropped. Automated tests use generated loopback replica sets with explicit cleanup guards, never MONGODB_URI.
